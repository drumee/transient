# Phase 4.6 plan — platform bootstrap contract and system-mfs

Phase 4.6 is the next implementation phase after the closed Phase 4.5
exportability lock. This document records its boundary only; it implements no
bootstrap operation, MFS code, schema, package or application.

## Goal and validation target

Define the minimal platform-bootstrap contract required to turn installed
runtime schemas into a valid minimal Drumee instance, then introduce MFS as the
first system/kernel module. The future validation target is a kernel that still
boots without MFS, plus deterministic capability failure for a module that
declares MFS as required.

## Platform invariants

```text
DEFAULT_ORG_ID = 1
NOBODY_UID = ffffffffffffffff
```

A valid instance contains:

- mandatory organisation `id = 1`;
- mandatory nobody `uid = ffffffffffffffff`;
- a mandatory provisioned guest, distinct from nobody;
- a mandatory provisioned privileged system identity, distinct from guest and
  nobody.

Organisation and nobody use canonical platform IDs. Guest and system do not:
their IDs remain generated by provisioning and resolved through existing
configuration state. No future module should invent hardcoded replacements.

Runtime may know, resolve and require these values and fail clearly if a valid
installation contract is broken. Runtime must never create or opportunistically
repair them during boot, request/session handling or schema installation.

## Lifecycle and ownership

```text
runtime package installation
→ intrinsic runtime schema installation
→ platform bootstrap
→ organisation 1 + nobody + guest + system
→ valid minimal Drumee instance
→ optional system-mfs capability
→ business applications such as Marketing
```

Ownership remains explicit:

- `server-runtime`: boot/runtime, session/authentication, Domain ACL, module
  loading/dispatch and intrinsic runtime schemas;
- platform bootstrap/control plane: decides when and for which context to
  orchestrate organisation `1`, nobody, guest and system provisioning;
- `system-mfs`: will own MFS runtime behavior, schemas, migrations and
  MFS-specific provisioning hooks, but not platform identity creation;
- Marketing: will own its business lifecycle and schemas, including Profile,
  Source, Crawl, Document, Claim, Evidence and Review;
- Finder: remains a future system application, not the MFS engine.

The rule for later phases is:

> Each module owns the knowledge required to install and provision its own
> resources, but the module does not decide when or for whom provisioning
> occurs.

The bootstrap/control-plane orchestrator makes those timing and target-context
decisions. No provisioning framework is selected or implemented by this plan.

## MFS preconditions and classification

`system-mfs` is a system/kernel module, not intrinsic runtime. It may require
organisation `1`, nobody, guest and system as preconditions, but must not create
them. The kernel remains independently bootable without MFS. A future declared
MFS dependency must fail deterministically when unavailable; the dependency
mechanism is intentionally deferred to Phase 4.6 implementation work.

## Non-goals

This planning boundary adds no MFS, Hub/resource ACL, storage, Finder, Window
Manager, Marketing, provisioning engine, organisation/identity creation code,
module lifecycle framework, SQL, npm package, ESM migration, Team migration or
deployment packaging.
