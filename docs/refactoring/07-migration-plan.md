# Migration Plan

No implementation phase begins without architectural approval. All later work remains beside immutable `sources/**`; rollback never rewrites the baseline. The immediate sequence prioritizes an application-neutral kernel over reconstruction of the integrated Team product.

| Phase | Goal and scope | Prerequisites / affected areas | Compatibility, tests and rollback | Control-plane and deployment impact | Risk / expected benefit |
|---|---|---|---|---|---|
| 0 — mapping approval | Approve evidence, target boundary and deliberately deferred questions. | Current mapping, source provenance and Phase 1 findings. | Documentation-only rollback; verify source hashes. | No runtime, CLI or deployment change. | Low / an auditable decision point. |
| 1 — baseline characterization | Preserve current Team, CLI, MFS, provisioning and Debian behavior as evidence. | Immutable sources and guarded Phase 1 environment. | Keep safe tests and the strict gate; record selected live contracts when baseline permits. | Baseline deployment/CLI behavior remains reference-only. | Critical / prevents unsupported claims later. |
| 1.5 — minimal-kernel stabilization plan | Select the smallest symbol-level seams for `server-runtime` and `ui-runtime`; distinguish generic dispatcher from Team policy and generic LETC from MFS/application kinds. Pin the infrastructure-contract reference. | Approved `14-minimal-kernel-plan.md`; exact source traces; `sources/setup-infra` provenance in `SOURCE_MANIFEST.md`. | Contract fixtures for existing ACL and `Kind.loadPlugin` flows; no source or target implementation in this planning phase. | Identify only stable future needs; no lifecycle API or package format. | Critical / prevents oversized runtimes, premature manifests and invented HTTP contracts. |
| 2 — first runtime extraction and kernel integration | Extract a minimal backend/frontend runtime beside the baseline, retaining current backend ACL descriptor/lazy-load behavior and frontend `index.json`/bundle behavior. `server-runtime` uses the current imported `server-essentials`, not the Team lockfile resolution. Validate it in a disposable **clean Debian runtime + configuration generated from pinned `setup-infra` + `server-runtime` + `ui-runtime`**. | Approval after Phase 1.5; minimal testable server/ui seams; documented Essentials API deltas; pinned `setup-infra` Nginx contract. | Run focused current-Essentials context, dispatch, authorization, plugin-resolution and Kind/addon tests; prove generated config, `nginx -t`, service routing and plugin/static routing. | 3 — `hello` vertical slice | Build exactly one synthetic module with `hello.ping` (optional `hello.echo`) and one minimal LETC widget. Do not introduce `acl_check.sql`, `user_permission`, `user_expiry`, MFS schemas or factory provisioning merely for this path; rollback by removing the isolated target slice only. | No lifecycle command or Team deployment requirement. | High / end-to-end proof that a new module can run without Team, database-backed ACL, MFS or Window Manager. |
| 4 — intentional minimal MFS | Add only MFS semantics, ACL, storage and frontend primitives proven necessary after `hello`. | Hello contracts stable; explicit storage/schema/provisioning evidence. | Add MFS semantic, storage-failure and selected compatibility tests; preserve Team MFS as reference until equivalence decisions are approved. | Map CLI/deployment impacts before API or install changes. | Critical / establishes the resource substrate without importing Finder or WM. |
| 5 — `marketing` | Deliver the first real application; each new need is classified before promotion into an Essentials/runtime/module layer. | Phase 4 capabilities actually required by marketing. | Marketing acceptance tests plus selected kernel contracts; module-owned schema/policy rollback. | Identify only the administrative/deployment contracts marketing demonstrably needs. | High / supplies useful pressure to stabilize the kernel. |
| 6 — kernel stabilization | Remove accidental marketing dependencies from kernel seams; version selected contracts. | Hello and marketing evidence. | Regression suite across both applications; compatibility decisions documented. | Define only stable control-plane/deployment inputs. | Critical / creates a reusable module host. |
| 7+ — Team migration | Migrate Team capabilities one module at a time, beginning only when their dependencies are proven. Finder/Window Manager follow MFS/resource analysis; chat, tasks and meetings retain owned schemas/policy. | Stable kernel plus module contracts; selected Team baseline evidence. | Coexistence adapters and focused Team reconstruction tests; rollback keeps baseline distribution available. | Align CLI/admin and self-hosting only as each selected contract stabilizes. | Critical / preserves valuable Team behavior without making it the kernel boundary. |
| Later — stable administration and artifact deployment | Establish authenticated control-plane contracts, module lifecycle if approved, and artifact-driven Docker/native install/upgrade/rollback. | Mature runtime/module contracts and evidence of parity needs. | DB/API parity, fresh/existing install and rollback tests; retain legacy DB behavior during transition. | Directly affects CLI and Debian deployment. | Critical / safe operations and reproducible self-hosting. |
| Final — repository-boundary approval | Rehearse history-preserving extraction after validated boundaries. | Stable runtime/modules/distributions and passing selected suites. | Extraction rehearsal and rollback plan. | Publish only approved artifact boundaries. | Medium / maintainable final repositories. |

Phase 1 facts do not disappear under this sequencing. The current authoritative Debian E2E blockage is a critical risk for later Team/self-hosting work, but it does not justify expanding the first no-Team `hello` kernel scope or copying Team policy into it.

## Phase 2 integration definition of done

In addition to the extraction checks above, Phase 2 cannot complete until all of the following are proven by reproducible test tooling:

- [ ] `sources/setup-infra` remains pinned at the SHA recorded in `SOURCE_MANIFEST.md` and immutable;
- [ ] a disposable kernel environment consists of a clean Debian runtime, configuration generated from that source, `server-runtime`, and `ui-runtime`;
- [ ] generated configuration is inspectable under `.tmp/test-env/kernel/` (or an equivalent disposable container root), never under `sources/**` or host `/etc`;
- [ ] `nginx -t` succeeds against the generated configuration;
- [ ] `server-runtime` starts without `server-team` and `ui-runtime` artifacts are served without `ui-team`;
- [ ] a required Drumee service route reaches `server-runtime`, and a required frontend plugin/static route reaches `ui-runtime`;
- [ ] no `sources/debian` Team image is used as the new-kernel host;
- [ ] schemas, MFS and factory provisioning have not been introduced solely to make the anonymous fast ACL path executable;
- [ ] the integration environment is documented, reproducible and leaves the historical Debian baseline available as separate evidence.

This definition of done deliberately does not run `hello`; that remains the first Phase 3 vertical-slice proof.
