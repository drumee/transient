# WireGuard peer coordination

Lets a Drumee node be reached from outside **without opening a port on the
user's router**. Shipped by `drumee-infra`, disabled by default.

## Why it exists

Plugging a box into a home LAN solves *addressing* for free — SLAAC hands it a
globally routable IPv6 address in seconds, no router admin needed. It does not
solve the *inbound firewall*: virtually every consumer router drops unsolicited
inbound connections, so `:443` on that address is unreachable.

Outbound always works, though. A stateful firewall lets return traffic back in
for a connection the inside host opened. Coordination exploits exactly that:
the node holds an outbound connection to a coordination server; when a client
wants to reach it, both sides are told the other's public address and fire
their WireGuard handshake at the same instant, so each firewall opens its own
return pinhole. The result is a direct, end-to-end encrypted peer-to-peer
tunnel. The coordination server never sees traffic content.

## Components

| Piece | Where | Role |
|---|---|---|
| `bootstrap.sh` | `/var/lib/drumee/wireguard/` | First boot: generate keypair, bring up `wg0` on a fixed port |
| `agent.js` | `/var/lib/drumee/wireguard/` | Long-lived: probe reflector, register, program peers |
| `drumee-wg-bootstrap.service` | systemd | oneshot, ordered before the agent |
| `drumee-wg-agent.service` | systemd | `Restart=always`, `CAP_NET_ADMIN` only |
| `wireguard.json` | `/etc/drumee/conf.d/` | Generated by postinst from debconf — **not** a conffile |

The private key is generated on the device and never leaves it. Only the public
key is sent to the coordination server.

## Configuration

Declarative, via `config/drumee.yaml`:

```yaml
wireguard:
  enabled: true
  coordinator: coord.drumee.tech
  listen_port: 51820
  reflector_port: 51821
```

```bash
node config/render.mjs debconf --config config/drumee.yaml > install.conf
debconf-set-selections < install.conf
apt install drumee
```

Interactively, `apt install drumee-infra` asks the same questions — but only
when `local_mode` is false, since NAT traversal is meaningless on a LAN-only
instance. `render.mjs validate` rejects the combination outright.

To change it later: `dpkg-reconfigure drumee-infra`.

## Why the listen port must stay fixed

The agent learns its public `IP:port` by probing the coordination server's UDP
reflector, which echoes back what it observes. That mapping is only useful if
the probe leaves from the **same** port WireGuard will use. A random port would
produce a mapping that points nowhere.

## Requirements and known limits

- **Node >= 22** for the agent (it uses the global `WebSocket`). The package
  only requires `nodejs >= 20` for the rest of the stack, so postinst checks
  explicitly and leaves coordination disabled with a clear message rather than
  installing a service that crash-loops at boot.
- **Symmetric NAT** defeats the reflector: the mapping differs per destination,
  so the observed one won't work for the peer. These sessions fall back to the
  relay. This is a known limit, not a bug.
- **Relay fallback** requires `WG_RELAY_PUBKEY` and `WG_RELAY_HOST` on the
  coordination server. Unset, the server reports a clear failure instead of
  pretending to relay.
- IPv4-only client networks cannot reach an IPv6-only published node.

## Operating

```bash
systemctl status drumee-wg-agent
journalctl -u drumee-wg-agent -f
wg show wg0                       # peers and last handshake times
cat /etc/drumee/credential/wireguard/public.key
```

A non-zero `latest handshake` for a peer means the direct tunnel is up. If
peers keep appearing only via the relay, check whether the ISP applies
symmetric NAT.
